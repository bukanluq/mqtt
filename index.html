ESP32-S3 · LESSON 8

MQTT: Publish & Subscribe

You've had the ESP32-S3 talk to Blynk's dashboard. Today you learn the protocol running underneath most real IoT products — MQTT — and use it directly, with no dashboard service in between.

Before this lesson: students should be comfortable with Wi-Fi connection code, pinMode() / digitalWrite() / analogRead(), and reading Serial Monitor output.
Part 1 · Concepts

What is MQTT, actually?

MQTT is a lightweight messaging protocol built for devices with weak connections and small processors — exactly what an ESP32-S3 is. Instead of devices calling each other directly, everyone talks through one central server.

  • A device publishes a message to a named topic — it doesn't need to know who (if anyone) is listening.
  • Other devices subscribe to that topic and get the message the moment it arrives.
  • The server in the middle — the broker — is the only thing every device needs to know how to reach.
Why it matters: this is the same pattern running under most commercial smart-home and industrial IoT products. Learn it once here, and it transfers directly — Blynk itself is built on MQTT-like ideas under the hood.

How the pieces talk to each other

Nothing connects directly to anything else. Every device — publisher or subscriber — only ever talks to the broker.

  • A device opens one connection to the broker and keeps it open — that's what client.loop() maintains.
  • Publishing sends a message to a topic; the broker instantly forwards it to every current subscriber of that topic.
  • The same device can publish to one topic and subscribe to another at the same time, over that one connection.
Part 1 · Concepts

Five words you'll keep hearing

BrokerThe server every device connects to. It has no idea what your data means — it just routes messages from publishers to subscribers by topic.
TopicA message's address, written like a file path — e.g. e21/lesson8/sensor. Publishers and subscribers just need to agree on the exact string.
PayloadThe actual message content, sent as plain text or bytes — a number, a word like "ON", or a small JSON string.
Client IDA name your device gives itself when connecting. Two devices connecting with the same Client ID will keep kicking each other off — always make it unique.
QoS & RetainedTwo optional delivery settings. This lesson uses the simple defaults (QoS 0, not retained) — good enough for almost everything you'll build early on.

Setup 3 of 3 — Code

Full sketch: private broker (TLS)

Credentials, pins & functions
#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <PubSubClient.h>

const char* ssid = "YourWiFiName";
const char* password = "YourWiFiPassword";

const char* mqttServer = "xxxxxxxx.s1.eu.hivemq.cloud";
const int mqttPort = 8883;
const char* mqttUser = "YourMqttUsername";
const char* mqttPass = "YourMqttPassword";
const char* clientId = "esp32s3-client-04";

WiFiClientSecure espClient;
PubSubClient client(espClient);

const int ledPin = 4;
const int sensorPin = 5;

unsigned long lastPublish = 0;
const unsigned long publishInterval = 2000;

void callback(char* topic, byte* payload, unsigned int length) {
  String message;
  for (unsigned int i = 0; i < length; i++) {
    message += (char)payload[i];
  }
  if (message == "ON") digitalWrite(ledPin, HIGH);
  else if (message == "OFF") digitalWrite(ledPin, LOW);
}

void reconnect() {
  while (!client.connected()) {
    if (client.connect(clientId, mqttUser, mqttPass)) {
      client.subscribe("e21/lesson8/led");
    } else {
      delay(2000);
    }
  }
}
setup() and loop()
void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);

  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
  }

  espClient.setInsecure();
  client.setServer(mqttServer, mqttPort);
  client.setCallback(callback);
}

void loop() {
  if (!client.connected()) {
    reconnect();
  }
  client.loop();

  unsigned long now = millis();
  if (now - lastPublish > publishInterval) {
    lastPublish = now;
    int sensorValue = analogRead(sensorPin);
    char payload[8];
    itoa(sensorValue, payload, 10);
    client.publish("e21/lesson8/sensor", payload);
  }
}
What changed from Activity 3: WiFiClientSecure replaces WiFiClient — it speaks TLS, which port 8883 requires. client.connect() now takes a username and password as extra arguments. setInsecure() is a shortcut that skips verifying the broker's certificate — fine for learning, but a production device should instead load the broker's real root certificate.
Part 2 · Arduino IDE Setup

Board & wiring — ESP32-S3

Board selection

Tools → Board → "ESP32S3 Dev Module" (not the plain "ESP32 Dev Module"). Everything else — Wi-Fi, MQTT, the Arduino API — behaves identically to a classic ESP32; only the board entry changes.

USB & upload mode

If uploading fails, check Tools → USB CDC On Boot is enabled, and hold BOOT while tapping RESET to force the board into upload mode.

Same two components as before — an LED to control, a sensor to read — on pins that are safe defaults on ESP32-S3 dev boards.

LED — output, pin 4

LED anode through a 220Ω resistor to GPIO4. LED cathode to GND.

Sensor — input, pin 5

LDR (or potentiometer wiper) forms a voltage divider into GPIO5. GPIO5 is a valid ADC1 input on the ESP32-S3 — a good fit for analogRead().

No sensor on hand? A potentiometer wired the same way works identically — turning it stands in for changing light.
Activity 1 of 3 — Code

Connect & publish sensor data

Credentials, pins & client
#include <WiFi.h>
#include <PubSubClient.h>

const char* ssid = "YourWiFiName";
const char* password = "YourWiFiPassword";

const char* mqttServer = "broker.hivemq.com";
const int mqttPort = 1883;
const char* clientId = "esp32s3-client-01";

WiFiClient espClient;
PubSubClient client(espClient);

const int sensorPin = 5;

void reconnect() {
  while (!client.connected()) {
    Serial.print("Connecting to MQTT...");
    if (client.connect(clientId)) {
      Serial.println("connected");
    } else {
      Serial.print("failed, rc=");
      Serial.print(client.state());
      Serial.println(" retrying in 2s");
      delay(2000);
    }
  }
}
setup() and loop()
void setup() {
  Serial.begin(115200);
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWiFi connected");
  client.setServer(mqttServer, mqttPort);
}

void loop() {
  if (!client.connected()) {
    reconnect();
  }
  client.loop();

  int sensorValue = analogRead(sensorPin);
  char payload[8];
  itoa(sensorValue, payload, 10);
  client.publish("e21/lesson8/sensor", payload);

  Serial.print("Published: ");
  Serial.println(payload);

  delay(2000);
}
Activity 1 of 3

Connect & publish sensor data

Connect to Wi-Fi, connect to the broker, then push a sensor reading to a topic every 2 seconds — this is the "device reports in" half of MQTT.

What's new: client.connect(clientId) opens the MQTT connection using your unique Client ID. client.publish(topic, payload) sends a message — the payload must be a C-string, hence itoa() to convert the number. client.loop() must run every pass of loop() to keep the connection alive.
Why a reconnect() function: Wi-Fi and MQTT connections drop sometimes — routers reboot, signal dips. This is the standard real-world pattern: check client.connected() every loop, and reconnect automatically if it's ever false.
Expected result: the Serial Monitor prints "Published: …" every 2 seconds. To see it arrive, open HiveMQ's free web MQTT client, connect to broker.hivemq.com, and subscribe to e21/lesson8/sensor.
Students: change the clientId to include your own name or student ID — if two people use the same one on the same broker, you'll keep disconnecting each other.

Activity 2 of 3

Subscribe & control the LED

A different sketch, on purpose: now the ESP32-S3 listens instead of talks. Anyone who publishes "ON" or "OFF" to the right topic switches your LED.

What's new: client.setCallback(callback) registers the function Blynk-style calls run automatically when a subscribed message arrives. callback() receives the topic and the raw bytes — rebuilding them into a String is the easiest way to compare against "ON"/"OFF". Subscribing happens inside reconnect(), right after connecting — a fresh connection has no subscriptions yet.
Expected result: publish the text "ON" to e21/lesson8/led from HiveMQ's web client (same one as Activity 1) and the physical LED turns on; publish "OFF" and it turns off.
Students: try publishing something other than exactly "ON" or "OFF" (like "on" lowercase) and see nothing happen — good moment to talk about how MQTT payloads are just bytes with no built-in meaning; your code decides what they mean.

Activity 3 of 3

Put it together: publish + subscribe

This is the pattern real devices actually run: one connection, publishing on one topic and subscribed to another, at the same time.

The one change from delay() to millis(): Activity 1 used delay(2000) between publishes because nothing else was happening. Here, a 2-second delay() would freeze client.loop() for 2 full seconds — the LED would lag behind incoming messages. lastPublish / millis() checks the clock without ever blocking, so subscribed messages still arrive instantly.
Expected result: the LED responds to ON/OFF messages the instant you send them, while the sensor reading keeps publishing every 2 seconds in the background — neither task waits on the other.
Students: watch the Serial Monitor and the web MQTT client side by side — publish an LED command mid-way through a sensor delay and confirm it reacts immediately, not after the next 2-second tick.
Part 3 · Testing

Talking to your ESP32-S3 without writing a second sketch

You don't need a second device to test either direction — a free web MQTT client plays the role of "the rest of the world."

  1. Open HiveMQ's free web MQTT client.No install, no account — it's a browser-based publish/subscribe tool.
  2. Connect it to broker.hivemq.com, port 8884 (WebSocket).The web client needs the WebSocket port, not 1883 — your ESP32-S3 keeps using 1883, that part doesn't change.
  3. Subscribe to e21/lesson8/sensor to watch your device publish.
  4. Publish "ON" or "OFF" to e21/lesson8/led to control your device.
Everyone in class using the same public broker and similar topic names? Add your name to the topic — e.g. e21/lesson8/luqman/sensor — so you're not all reading each other's messages.
